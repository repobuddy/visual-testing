Updating baselines

A baseline changes in two cases: it does not exist yet, or the UI changed on purpose.

A baseline does not exist

Section titled “A baseline does not exist”

By default a snapshot without a baseline fails with has no baseline image. Please review the new snapshot and update the baseline image. and the message names the result file. Two things write the missing baseline:

  • Run Vitest with -u. Vitest sets its snapshot update mode to all.
  • Pass createMissingBaseline: true to the matcher, or set it with vis.setup({ createMissingBaseline: true, auto: ... }). It writes only the baselines that are missing and leaves existing ones alone.

createMissingBaseline suits a first run or a bot that fills in new tests. -u suits the moment you have reviewed everything. The options are in toMatchImageSnapshot().

In Storybook with storybook-addon-vis, the matcher options travel over RPC and a custom field such as createMissingBaseline may not reach the server. Use -u there. See Get started with the Storybook addon.

The UI changed on purpose

Section titled “The UI changed on purpose”

A mismatch fails the test and writes the diff and review image. With -u, a mismatch overwrites the baseline with the result instead of failing, unless the snapshot has expectToFail.

  1. Run the tests and open the failures. Decide that each change is intended.
  2. Run vitest -u (or vitest run -u) on the platform whose baselines you commit.
  3. Look at the changed baseline images in git diff or your pull request.
  4. Commit them with the code change.

Run -u only after you reviewed the failures. It accepts every difference, including a regression you did not notice.

Obsolete baselines

Section titled “Obsolete baselines”

A baseline becomes obsolete when its test is renamed or removed, takes fewer snapshots, or its test file moves or is deleted. vitest-plugin-vis records every baseline a run uses. At the end of the run it lists the baselines in the run’s snapshot folders that the run did not use, like Vitest’s obsolete count for text snapshots:

With -u, it deletes them and any folder they leave empty, and prints removed instead of found. There is no option to turn this on.

It keeps a baseline when it cannot be sure the baseline is unused:

  • Snapshots of skipped, todo, and failed tests, and of tests filtered out by -t or .only. A test protects every file whose name starts with its task ID.
  • Every baseline of a test file that has errors of its own, such as a failed import or beforeAll.
  • Baselines of test files outside the run.
  • Snapshot folders the run did not use, such as other platforms (linux and win32 when you run locally) and projects that did not run.
  • File names shortened by shortenLongSnapshotPaths, which no longer start with a task ID.

Baselines of a test file that is gone are listed only when the run covered the snapshot folder in full: no --project filter, no file filter, --shard, or --changed, and no unhandled error. A run filtered that way still lists the unused baselines of the test files it ran. Nothing is listed or deleted when the run is interrupted or has an unhandled error.

In CI that runs with -u to collect new baselines, the deletions show up in the same changes as the updated baselines. Review them like any other baseline change.

Prune baselines of deleted test files

Section titled “Prune baselines of deleted test files”

A run sweeps the folders of deleted or moved test files only when it covers the snapshot folder in full, and only for the platform it runs on. vitest-plugin-vis prune removes those folders without running tests, for every platform folder (linux, win32, darwin, local, …):

With storybook-addon-vis, run storybook-addon-vis prune instead. The addon gets vitest-plugin-vis only as its own dependency, so the package manager may not link the vitest-plugin-vis command into your project. storybook-addon-vis prune runs the vitest-plugin-vis the addon depends on, with the same options and exit codes:

Use npx, yarn, or bunx in place of pnpm exec with other package managers. Do not run npx vitest-plugin-vis or pnpm dlx vitest-plugin-vis in an addon project: they can fetch a version from the registry that differs from the one your tests use.

It looks for __vis__ folders under the current folder and treats the parent of each one as the project root. A folder under __baselines__ that is named like a test file is orphaned when no file in the project maps to it. Without --dry-run it deletes those folders and any folder they leave empty.

It only finds test files that were deleted or moved. For renamed or removed tests in a test file that still exists, use a full vitest run -u.

It reads the vite.config.*, vitest.config.*, and .storybook/* files of each project root and its parent folders, up to the current folder:

  • When one sets snapshotSubpath, it refuses and deletes nothing, because baseline folders cannot be mapped back to test files.
  • When one sets shortenLongSnapshotPaths, it prints a warning. It always keeps folders with shortened names (Button-0123456789ab.tsx), with or without the option.
  • When no folder under a __baselines__ folder matches a test file, it refuses and deletes nothing. That happens when snapshotRootDir or the project root does not match this layout.

The check reads the option names in the file text. An option set in a file that the config imports is not seen. It exits with 1 when it refuses.

Let an agent clean up

Section titled “Let an agent clean up”

Both packages ship the remove-obsolete-image-snapshots agent skill. It tells a coding agent to run the full suite, check each listed baseline for tests that run only on some platforms or runs, and keep those baselines before it removes the rest. It uses vitest-plugin-vis prune, or storybook-addon-vis prune in the addon, for the folders the run cannot see.

With several platforms

Section titled “With several platforms”

Each platform has its own baselines, so update each one. Platforms and CI describes how to do that in CI.

Review before merge

Section titled “Review before merge”

A reviewer should see the changed baselines in the pull request. For dependency bots that merge themselves, make the check fail when a baseline changes, so a rendering change does not pass unreviewed.
